# Independent Audit — Grouping Messages

**Audit date:** 2026-11-20  
**Commit:** `c903f35` (`master`, `feat: add sms search and filtering support`)  
**App version:** 1.6 (`versionCode` 16), DB schema v3, `minSdk` 24, `targetSdk` 36  
**Auditor:** independent pass, not derived from the existing `improvements.md` backlog

This audit covers the app, its data and privacy boundary, the release pipeline, and
readiness for F-Droid and IzzyOnDroid. It is deliberately hostile: the question is not
"does it work on the happy path" but "what breaks, leaks, or cannot be shipped".

---

## 1. Executive verdict

**Do not submit to F-Droid or IzzyOnDroid, and do not publish a release, until the P0
items in §4 are fixed.**

> **Update (same day):** the P0/P1 items marked below were implemented in the working
> tree. See `docs/REMEDIATION_PLAN.md` for the change list and verification. Treat this
> document as the original audit record; the plan is the current state.

The app's core is sound: it is a small, pure-Java, single-module app; SMS text stays
on-device; it has no analytics, no WebView, no dynamic code loading, and no exported
service. The 102 JVM tests pass. A clean unsigned release build is byte-identical on
repeat builds locally.

The blockers are distribution and one privacy leak, not the classifier:

1. the release workflow computes versions from the moving `latest` tag, so it produces
   a malformed version and can only move backwards in `versionCode`;
2. it never creates or pushes the git tag that F-Droid/Izzy must build from;
3. it writes the signing key into the repository working tree and never removes it;
4. one error path logs the complete SMS row, including sender and body;
5. there is no F-Droid recipe, no Fastlane metadata, and no store asset validation.

## 3. What is genuinely good, and must be preserved

- **On-device only.** `ExternalContentBridge` reads the SMS provider; no message text is
  posted anywhere. The only outbound call is the update check in `SettingsViewModel`.
- **No analytics, crash reporting, ads, WebView, reflection-driven plugins, or dynamic
  code loading.**
- **No exported activity/service that handles SMS.** `MainActivity` is exported only for
  the launcher. `SmsActivity`, `SettingsActivity`, and `ChangeCategoryActivity` are
  `exported="false"`. The `FileProvider` is `exported="false"`.
- **Backups are off at the OS level** (`android:allowBackup="false"`).
- **Atomic database replacement.** `DatabaseBackup` writes `.tmp`, verifies a SQLite
  header, then renames; export drains the WAL first.
- **No raw SQL string concatenation with user input.** Selections are parameterized
  except internal literal predicates and `IN (...)` placeholder construction.
- **102 JVM tests**, including schema, migration, DAO, backup, classification parity,
  version check, and search tests.
- **Deterministic unsigned release build** verified locally.
- **Simple, readable layering** (`Activity` -> `ViewModel` -> DAO) with no framework
  churn. Do not rewrite this into Compose/Room/Hilt for the sake of an audit.

## 4. P0 — release and distribution blockers

| ID | Finding | Evidence | Impact |
|---|---|---|---|
| A-01 | Release version is calculated from the **moving `latest` tag** | `.github/workflows/release.yml:34` uses `git tag --sort=-v:refname \| head -n 1`; the repository has a `latest` tag | Next tag becomes `vlatest.0.1` (or arithmetic failure in Bash); `versionName`/`versionCode` become invalid or non-monotonic. F-Droid will reject the version code. |
| A-02 | The workflow never creates or pushes the tag it claims to release | `release.yml:48-57`, `:67-74`; `softprops/action-gh-release` is given `tag_name` but no `git tag`/`git push` step exists | F-Droid's `commit:` cannot resolve a release tag; Izzy cannot reproduce the artifact; the GitHub release may create a tag only as a side effect, with different semantics. |
| A-03 | Signing key is decoded into the repository working tree and never removed | `release.yml:24-28` writes `app/app-release.jks`; no cleanup step | A later artifact/upload/workspace capture can leak the release key. This is a supply-chain incident, not a lint nit. |
| A-04 | Release publishes without tests or lint | `release.yml:6-74` has no `testDebugUnitTest` or `lintDebug` | A regression can ship straight to F-Droid/Izzy. |
| A-05 | No F-Droid recipe, no Fastlane metadata, no store validation | absence of `metadata/`, `fastlane/`; no workflow checks them | The app cannot be submitted as-is; there is no machine check that store assets match the APK. |
| A-06 | Debug workflow forcibly moves the `latest` tag on every push | `.github/workflows/master_debug_release.yml:40-46` uses `tag_name: latest` | This is the root cause of A-01. It also makes the release tag mutable and races the release job. |
| A-07 | Full SMS row is logged on insert failure | `app/src/main/java/in/rahulja/groupingmessages/db/SmsDao.java:130-133` logs `trainedSmsMap.toString()` (address, body, IDs) | Message content leaks into logcat, bug reports, and any log collector. Contradicts the README privacy claim. |
| A-08 | Release version defaults and docs disagree with the build | `build.gradle:18-19` says 1.6/16; `README.md:12` says target/compile 35; `app/build.gradle` compiles 36; `BASELINE.md` cites 34 | Local builds, docs, and F-Droid recipe can diverge; reviewers cannot tell what shipped. |

**P0 exit criteria**

- Release trigger is a `vX.Y.Z` tag; the same tag is created and pushed before the
  build; the workflow refuses any other tag shape.
- `versionCode = X*10000 + Y*100 + Z` and is greater than the published code.
- Signing key exists only under `$RUNNER_TEMP`, is removed in an `if: always()` step,
  and is never under the checkout directory.
- Release runs unit tests + lint; the artifact is signature-verified and manifest-checked.
- No SMS body/address appears in any `Log.*` call.
- Debug rolling release uses `debug-latest`, never `latest`.

## 5. P1 — security, privacy, and data integrity

| ID | Finding | Evidence | Impact / fix direction |
|---|---|---|---|
| B-01 | Inbox rows are ingested without the provider `_ID`; duplicates are possible | `ExternalContentBridge.java:31-41` projection omits `_ID`; `SmsDao.java:107-153` inserts without conflict handling | Reopening the app can duplicate messages; the `lastSmsTime` watermark uses `date > last`, so equal-timestamp messages are missed. Add `_ID`, `insertWithOnConflict(..., CONFLICT_IGNORE)`, and `>=`/ID-based watermark. |
| B-02 | Config read can crash on a restored/foreign database | `ExternalContentBridge.java:28`, `SmsDao.java:110` do `Long.parseLong(ConfigDao.getValue(...))`; `ConfigDao.getValue` returns `null` when absent | `NumberFormatException` on import of an older/hand-made DB. Add a typed default and a null-safe reader. |
| B-03 | Foreign keys are declared but never enforced | `DatabaseContract.java:182-185`; `DatabaseHelper.java` has no `onConfigure`/`onOpen` `foreign_keys` pragma | Orphan `category_id`/`similar_to` rows are accepted. Add a v4 cleanup migration, enable FK after upgrade, and test rejection. |
| B-04 | Backup export/import is a fixed file in app-specific external storage, not user-selected storage | `DatabaseBackup.java:27-29`, `:45-105`; `SettingsFragment.java:145-151`, `:213-227` | Users must find the path manually; the DB is a plaintext file outside the app sandbox. Replace with Storage Access Framework create/open document streams. |
| B-05 | Import validates only the 16-byte SQLite header | `DatabaseBackup.java:107-128`; `verifySqliteHeader` | A well-formed but foreign/hostile SQLite file is installed and opened. Validate `PRAGMA integrity_check`, `user_version <= DATABASE_VERSION`, and required tables/columns on a scratch copy before the swap. |
| B-06 | Import closes the singleton database while other threads may still hold cursors | `DatabaseBackup.java:49-68`; `AppDatabase.java:15-22` documents "no readers" but does not enforce it | A background sync/search can hit a closed DB during import. Serialize all DB access through one executor or a read/write lock for the swap. |
| B-07 | `FileProvider` path is the whole external files directory; share MIME is `*/*` | `app/src/main/res/xml/file_paths.xml:3-6`; `SettingsFragment.java:286-308` | Over-broad URI grant surface for a database containing all SMS. Narrow the path to the backup file and use a specific MIME type. |
| B-08 | `READ_CONTACTS` is mandatory at startup | `MainActivity.java:178-183`, `:346-354` | The app refuses to run if the user denies contact access, although contacts are only a display-name nicety. Make contacts optional; SMS remains required. |
| B-09 | Update check runs automatically on opening Settings, with no consent | `SettingsFragment.java:72-81`; `SettingsViewModel.java:39-67` | A network request reveals app use to GitHub on every Settings open. Make it opt-in (default off) and validate the redirect target. |
| B-10 | Update comparison does not normalize the `v` prefix | `SettingsViewModel.java:53-58` compares `/releases/tag/` + `VERSION_NAME` against the redirect target; current tags are `1.6`, next tags are `v1.7.0` | After moving to `vX.Y.Z` tags, a fully updated app reports "outdated" forever. Normalize tag labels. |
| B-11 | Database work on the main thread | `CategoryListItemHolder.java:118-120`; `SmsListItemHolder.java:109`; `ChangeCategoryActivity.java:37`; `MainActivity.java:315` | ANR/jank risk on slow storage or a large DB. Route through the existing ViewModel/DAOs and `AppExecutors`. |
| B-12 | No `FLAG_SECURE` on the SMS list | absence in `SmsActivity.java` | Message text appears in the recent-apps thumbnail and in screenshots. Add the flag on the message screen. |
| B-13 | Backups are plaintext SQLite | `DatabaseBackup.java`, `SettingsFragment.java` export flow | Anyone who obtains the backup gets every message. Decide explicitly: SAF + warning for 1.7, optional passphrase-encrypted backup for 1.8. Do not add SQLCipher casually; it changes schema/migration and F-Droid reproducibility. |
| B-14 | No Android 12+ data-extraction rules | `AndroidManifest.xml:12`; lint `DataExtractionRules` warning | `allowBackup=false` is correct today, but the platform expects explicit rules. Add `dataExtractionRules` and `fullBackupContent="false"`. |
| B-15 | Contact lookup can return a null display name for a null address | `ExternalContentBridge.java:121-129`; `SmsListArrayAdapter.java:98-101` | `HashMap.get(null)` then `setText(null)`; a row can show blank or throw in later formatting. Normalize null/blank addresses to a placeholder. |
| B-16 | Version check runs on the same single-thread executor as all DB work | `AppExecutors.java:10-14`; `SettingsViewModel.java:40` | A 10-second network timeout blocks DB, sync, and backup tasks. Use a separate network executor or a bounded I/O pool. |
| B-17 | No static guard against SMS content in logs | no Error Prone/checkstyle/CI grep | The A-07 class of bug can return. Add a CI rule and a review checklist. |

## 10. Security threat model (short form)

**Assets:** SMS body and address, contact display names, category assignments, the
training corpus, the SQLite file, and the exported backup.

**Adversaries and controls:**

| Threat | Current control | Remaining gap |
|---|---|---|
| Another app reads the DB | App sandbox; no exported content provider | Root/ADB or a device backup can still read it; at-rest encryption is a deliberate later decision. |
| Another app launches internal screens | All SMS screens `exported=false` | None for current manifest. |
| Another app reads the export | `FileProvider` `exported=false`; URI grant is per-share | Path is too broad; user can share to any app. Narrow path + MIME + warning. |
| Malicious SMS text | Plain `TextView`, no HTML/JS, no auto-link | Very low; no parser execution. |
| Malicious backup file | 16-byte header check | Needs full schema/integrity validation. |
| Network observer | HTTPS to GitHub; no message data sent | Update check is automatic; redirect target not validated; optional opt-in. |
| Log reader | Mostly IDs only | A-07 leaks full rows. Remove and gate. |
| Lost/stolen unlocked device | Android lock screen | No `FLAG_SECURE`; recent-apps thumbnail exposes text. |
| Supply chain | GitHub Actions, Gradle wrapper | Key in workspace, unpinned actions, no wrapper validation, no lockfiles. |

**At-rest encryption decision:** Do not add SQLCipher to 1.7. It changes the DB file
format, native dependencies, migration, backup/restore, and F-Droid reproducibility.
For 1.7, rely on Android's file-based encryption and app sandbox, remove OS backup, and
make export explicit and warned. Add optional passphrase-encrypted backup in 1.8. If
full DB encryption is later required, treat it as its own migration project with a
tested restore path.

## 12. What this audit does not claim

- It does not prove the classifier is accurate for every language or sender pattern;
  that needs a labelled corpus.
- It does not prove F-Droid's buildserver will accept AGP 9.3.1 and SDK 36.
- It does not replace a device test of permission denial, process death, or a real
  multi-GB message store.
- It does not authorize publishing. The P0 items are prerequisites.
